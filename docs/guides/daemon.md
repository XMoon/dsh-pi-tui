# Run dsh-pi-tui in daemon mode

Daemon mode gives one DSH Profile an independently running local Host and a
terminal Client that attaches to it. The Host can keep sessions and turns alive
after the terminal Client disconnects. It is a **local** Linux/macOS mode,
not a remote-network login or a second session authority.

## Select a backend

Direct is the default. To try daemon mode for a single interactive launch:

~~~sh
DSH_PI_TUI_BACKEND=daemon dsh --profile pi-tui
~~~

Alternatively, set **/settings → General → Backend** to `daemon`
and start a new TUI. This stored setting applies on the next launch only;
it does not change the backend of a Client already running. A one-launch
`DSH_PI_TUI_BACKEND` override has precedence over the Profile setting and
does not write it back.

Daemon mode requires a real interactive TTY and a supported Linux or macOS
system. A supported daemon launch authenticates or starts the Profile's one
Host as necessary; it does **not** automatically install a system service.

## Leave a Client or stop the Host

In daemon mode, `/exit` (alias `/quit`) closes the terminal Client; it is
**not** the same as stopping the Profile's background Host. A detached Host
may still have active work. For a deliberate Host shutdown use
`dsh --profile pi-tui daemon stop`.

This distinction is different in Direct mode, where the TUI owns its
in-process session lifecycle. Do not use a process kill or a guessed PID
as a replacement for the authenticated Profile control commands.

## Inspect and manage one Profile

All commands below select the same Profile explicitly:

| Intent | Command |
|---|---|
| Inspect Host and manager state, including ACP when provable | `dsh --profile pi-tui daemon status` |
| Start the Profile Host when needed | `dsh --profile pi-tui daemon start` |
| Stop the verified Profile Host | `dsh --profile pi-tui daemon stop` |
| Restart with manager/identity checks | `dsh --profile pi-tui daemon restart` |
| Inspect available Host logs | `dsh --profile pi-tui daemon logs` |
| Install the optional user service definition | `dsh --profile pi-tui daemon install` |
| Remove the owned user service definition | `dsh --profile pi-tui daemon uninstall` |

`status` and `logs` are read-only observations: they neither create nor
start a Host or service definition. A manager's “running” state alone is
not Host readiness; an authenticated Host identity is required. If an
installed unit belongs to a different profile or its manager source is not the
Profile unit, control operations refuse rather than taking over an unknown
process. A same-Profile service definition generated by a historical install
build remains manageable on both Linux and macOS; the recorded install build is
provenance, not an ownership requirement. `status` reports
`compatibility=other-build` when the observed build differs from the installed
profile.

## Read the raw qualification records

`daemon logs` normally shows concise Host production lines (ready, startup or
cleanup failures, warnings and stop). A Host process started with
`DSH_PI_TUI_ENTRY_RECORDS=1` in its own environment writes the raw entry-record
JSONL stream instead, one JSON object per line.

The variable is read once when a Host process starts. It is not a Profile
setting, a management command or a runtime toggle, it never changes an already
running Host, and a value set only on the `dsh daemon start` command does not
reach a Host launched by systemd or launchd. For a managed Host, set it in that
service's environment (for example a systemd user-service drop-in with
`Environment=DSH_PI_TUI_ENTRY_RECORDS=1` followed by
`systemctl --user daemon-reload`, or the LaunchAgent environment) and restart
the Host explicitly. Raw records are debugging output containing internal
profile details; do not publish them.

## Optional OS supervision

Without a service definition, daemon mode can still use the independent
Host process. `daemon install` is an **explicit** opt-in to profile-scoped
supervision: a verified systemd user unit on Linux or a user LaunchAgent on
macOS. Installing the definition is not an implicit start, enable or
restart, and does not migrate a live Host into a new manager.

The `daemon stop`, `restart` and `uninstall` operations can interrupt
Host work. Check `daemon status` and the running sessions first.

From the TUI, `/settings → General → Backend` saves the same Profile
preference (applies on the next launch). After a verified save to `Daemon`,
the same settings screen offers the optional service install as a separate
explicit action — `Not now` performs zero management IO, and one `Install`
confirmation runs exactly one profile-scoped install. The install never
starts, enables or migrates a running Host.

When a running Daemon Client saves `Direct` and then exits, it asks once
about the old Host: `Leave daemon Host running and exit` (the default) detaches
without touching the Host, and only the explicit `Stop daemon Host and exit`
runs the authenticated `daemon stop` after the terminal is restored. The stop
interrupts every connected Client, Session and Job of that Profile's Host.

## Adopt an installed update (Linux / macOS)

Package updates belong to the official plugin command. The daemon never
self-updates, and a normal plugin install does not stop the running Host:

~~~sh
dsh plugin --profile pi-tui -- add @xmoon76/dsh-pi-tui@<version>
~~~

This section covers a PiTui package update within the SAME DSH runtime and
Profile. The running Host keeps its actual build; a normal install does not
replace it. A compatible newer Client can attach to the still-running older
Host under the same required Host/Client wire protocol (`dsh-pi-tui/local/2`)
and exact DSH runtime. To adopt the currently installed build as the Profile
Host, restart it explicitly:

~~~sh
dsh --profile pi-tui daemon restart
~~~

This stops the verified Profile Host, waits for its kernel process to exit, and
starts a fresh managed Host from the current install. On Linux a systemd unit
generated by an older install is updated in place only for its recognized
generated launch entry and install-build metadata; its other bytes, mode and
user drop-ins are preserved. On macOS the same bounded migration applies only
to a LaunchAgent whose decoded `ProgramArguments` is provably the product's
generated entry; every other byte, comment, key and user-customized argument is
preserved. A user-custom `ExecStart` or launch command is executed as written,
so the running Host may still report `compatibility=other-build` until the user
points it at the current install. An old install-build record never requires
`daemon uninstall` before an explicit restart. `restart` is an explicit user
interruption: it can interrupt a running Session, Job or Interaction and does
not promise that in-flight work survives the Host change.

Changing the DSH runtime itself is not a hot upgrade. For a published old
pairing, finish in-flight work, back up the Profile and data, stop the old
Host, and install a supported DSH/TUI pair before a cold start; see the
[DSH compatibility guide](dsh-compatibility.md) and the release notes. Do not
read this same-DSH update path as a cross-DSH migration guarantee.

A service definition belongs to the current Profile. On both platforms the user
may manage it through the native system service tools; the product preserves
user-written bytes and only updates a recognized product-generated legacy
launch field during an explicit start or restart.

## Optional local ACP listener

The split Host can expose an optional Host-owned ACP v1 listener, which is
default-off. It is not a Direct-backend listener or a second Host authority. Its Profile auto-start preference and the **current**
running listener state are separate controls. `daemon status` shows a
socket address only for a listener that has been positively verified as
enabled; never guess a socket from the home/profile path.

From an attached Split Client, `/acp` can inspect or change the current
listener state without creating a Session or updating the next-launch
preference. The Direct backend refuses that runtime control.

For contributor-level process, authentication, ACP admission and Client
detach guarantees, see [Host/Client](../architecture/host-client.md),
[daemon process ownership](../architecture/host-daemon.md) and
[ACP listener contract](../architecture/host-acp.md).
