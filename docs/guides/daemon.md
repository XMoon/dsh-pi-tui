# Run dsh-pi-tui in daemon mode

Daemon mode gives one DSH Profile an independently running local Host and, on
Linux, macOS and native Windows 11 x64, a terminal Client that attaches to it.
The Host can keep sessions and turns alive after the terminal Client
disconnects. It is a **local** mode, not a remote-network login or a second
session authority. On Windows the supported domain is an ordinary (non-elevated)
user and an ordinary local fixed-NTFS profile path; service install/uninstall
and ACP remain unavailable. The same independent Host, management commands and
official Web frontend work as on Linux/macOS.

## Select a backend

Direct is the default. To try daemon mode for a single interactive launch:

~~~sh
DSH_PI_TUI_BACKEND=daemon dsh --profile pi-tui
~~~

PowerShell:

~~~powershell
$env:DSH_PI_TUI_BACKEND='daemon'; dsh --profile pi-tui
~~~

Alternatively, set **/settings → Host → Backend** to `daemon`
and start a new TUI. This stored setting applies on the next launch only;
it does not change the backend of a Client already running. A one-launch
`DSH_PI_TUI_BACKEND` override has precedence over the Profile setting and
does not write it back.

Daemon mode requires a real interactive TTY on every supported platform. A
supported daemon launch authenticates or starts the Profile's one Host as
necessary; it does **not** automatically install a system service. On Windows a
launch from a real ConPTY terminal (Windows Terminal, PowerShell console, or a
real terminal host) is supported; a redirected/no-TTY launch fails closed. On
the Windows supported domain the terminal Client is a native process attached
to the same independent Host; closing it or using `/exit` leaves the Host
running, and only the explicit commands below stop it.

## Leave a Client or stop the Host

In daemon mode, `/exit` (alias `/quit`) closes the terminal Client; it is
**not** the same as stopping the Profile's background Host. A detached Host
may still have active work. For a deliberate Host shutdown use
`dsh --profile pi-tui daemon stop`.

This distinction is different in Direct mode, where the TUI owns its
in-process session lifecycle. Do not use a process kill or a guessed PID
as a replacement for the authenticated Profile control commands.

## Inspect and manage one Profile

All commands below select the same Profile explicitly:

| Intent | Command |
|---|---|
| Inspect Host and manager state, including ACP when provable | `dsh --profile pi-tui daemon status` |
| Start the Profile Host when needed | `dsh --profile pi-tui daemon start` |
| Stop the verified Profile Host | `dsh --profile pi-tui daemon stop` |
| Restart with manager/identity checks | `dsh --profile pi-tui daemon restart` |
| Inspect available Host logs | `dsh --profile pi-tui daemon logs` |
| Install the optional user service definition (Linux/macOS only) | `dsh --profile pi-tui daemon install` |
| Remove the owned user service definition (Linux/macOS only) | `dsh --profile pi-tui daemon uninstall` |

`status` and `logs` are read-only observations: they neither create nor
start a Host or service definition. A manager's “running” state alone is
not Host readiness; an authenticated Host identity is required. If an
installed unit belongs to a different profile or its manager source is not the
Profile unit, control operations refuse rather than taking over an unknown
process. A same-Profile service definition generated by a historical install
build remains manageable on both Linux and macOS; the recorded install build is
provenance, not an ownership requirement. `status` reports
`compatibility=other-build` when the observed build differs from the installed
profile.

On Windows `daemon status`, `start`, `stop`, `restart` and `logs` operate on
the independent process: an authenticated Host reports `manager=process`; no
Host reports `manager=unmanaged`. `user-manager=not-checked`, `unit=none`, no
`systemctl`/`launchctl`, and `acp=unavailable`. `install` and
`uninstall` exit 3 before any scope or manager work because Windows has no
service manager in this contract.

`daemon logs` selects Host-process output only. A Split Client surface that
fails reports its own controlled line in the terminal and writes a private
incident file at `$DSH_HOME/logs/pi-tui-client/startup-*.log` (`DSH_HOME`
defaults to `~/.dsh`; `DSH_PI_TUI_LOG=off` suppresses the file). On Windows the
product-owned incident directory/file carry a protected owner-only DACL and the
shared `logs` parent is never chmodded or ACL-rewritten. `daemon logs` is not a
Client log entry. The incident file contains the real stack and private local
details; review it before sharing.

## Control the official Web frontend from the CLI

A running daemon Host can serve the official Web frontend. The headless CLI
inspects and controls that SAME Host without opening the TUI:

~~~sh
dsh --profile pi-tui daemon start
dsh --profile pi-tui web enable
dsh --profile pi-tui web url
~~~

The `web` verbs are supported on Linux, macOS and Windows. `web status` prints
`web=enabled`, `web=disabled`, `web=changing` or `web=unavailable`; `web
disable` withdraws the Web frontend again; `web open`
asks the default browser opener on the machine that runs the CLI to open the
authenticated URL. `web enable` never starts a Host: if the Host is not
running, every `web` command fails with `HOST_NOT_RUNNING` and asks you to run
`daemon start` first. An older Host build that predates the headless route is
reported as `WEB_CLI_UNAVAILABLE`; restart the Host from the current install to
adopt it.

The URL printed by `web url` contains a live Host launch token: treat it as a
temporary credential. It is printed only by that explicit command and is never
written to status output, logs or diagnostics. The product does not offer
automatic expiry, revocation or a short link, and it never modifies the
`127.0.0.1` address. To use it from another machine, set up your own SSH local
port forward to the Host machine and open the forwarded `127.0.0.1` URL there;
the token remains sensitive either way.

## Read the raw qualification records

`daemon logs` normally shows concise Host production lines (ready, startup or
cleanup failures, warnings and stop). A Host process started with
`DSH_PI_TUI_ENTRY_RECORDS=1` in its own environment writes the raw entry-record
JSONL stream instead, one JSON object per line.

The variable is read once when a Host process starts. It is not a Profile
setting, a management command or a runtime toggle, it never changes an already
running Host, and a value set only on the `dsh daemon start` command does not
reach a Host launched by systemd or launchd. For a managed Host, set it in that
service's environment (for example a systemd user-service drop-in with
`Environment=DSH_PI_TUI_ENTRY_RECORDS=1` followed by
`systemctl --user daemon-reload`, or the LaunchAgent environment) and restart
the Host explicitly. Raw records are debugging output containing internal
profile details; do not publish them.

## Optional OS supervision

Without a service definition, daemon mode can still use the independent
Host process. `daemon install` is an **explicit** opt-in to profile-scoped
supervision on Linux (verified systemd user unit) or macOS (user LaunchAgent);
Windows has no service definition and refuses `install`/`uninstall`. Installing the definition is not an implicit start, enable or
restart, and does not migrate a live Host into a new manager.

The `daemon stop`, `restart` and `uninstall` operations can interrupt
Host work. Check `daemon status` and the running sessions first.

From the TUI, `/settings → Host → Backend` saves the same Profile
preference (applies on the next launch). After a verified save to `Daemon`,
the same settings screen offers the optional service install as a separate
explicit action — `Not now` performs zero management IO, and one `Install`
confirmation runs exactly one profile-scoped install. The install never
starts, enables or migrates a running Host.

When a running Daemon Client saves `Direct` and then exits, it asks once
about the old Host: `Leave daemon Host running and exit` (the default) detaches
without touching the Host, and only the explicit `Stop daemon Host and exit`
runs the authenticated `daemon stop` after the terminal is restored. The stop
interrupts every connected Client, Session and Job of that Profile's Host.

## Host tool discovery (PATH)

A Host started by systemd, launchd or the detached launcher does not run an
interactive login shell. Before the official profile boot it appends the common
user and platform tool directories that already exist to its inherited PATH, so
Agent shells, background Jobs and child processes can find installed tools
without repeating `mise exec` or editing `.zshrc`. The inherited PATH keeps its
order: a tool directory already configured in the service PATH stays first, and
a same-name system tool may win. The durable contract is owned by the
[daemon architecture contract](../architecture/host-daemon.md#host-startup-environment);
the no-bootstrap escape hatch is `DSH_PI_TUI_HOST_PATH_MODE=inherit` in the
**actual Host environment**.

An existing managed Host already keeps its old process environment. After
upgrading, check that no important work is running and restart it; reinstalling
the service is not required:

~~~sh
dsh --profile pi-tui daemon status
dsh --profile pi-tui daemon restart
~~~

For a Linux systemd user unit, put the opt-out in a user drop-in below
`[Service]`, reload the manager and restart explicitly:

~~~ini
# ~/.config/systemd/user/dsh-pi-tui@<...>.service.d/50-host-environment.conf
[Service]
Environment=DSH_PI_TUI_HOST_PATH_MODE=inherit
~~~

~~~sh
systemctl --user daemon-reload
dsh --profile pi-tui daemon restart
~~~

For a macOS LaunchAgent, add `DSH_PI_TUI_HOST_PATH_MODE` with the value
`inherit` to that plist's `EnvironmentVariables` dictionary and restart with
the management command. A variable passed only to the `dsh daemon start` CLI
does not reach a Host started by systemd or launchd. For a detached cold start,
pass the variable in the calling shell; it does not change an already running
Host:

~~~sh
DSH_PI_TUI_HOST_PATH_MODE=inherit dsh --profile pi-tui daemon start
~~~

Inspect the Host's own environment from a connected Client (`!` or the Agent
Bash tool) with `command -v <tool>` or `printf '%s\n' "$PATH"`; do not publish
the complete environment. A tool that is installed later under a directory
that already existed is found without a restart; a newly created candidate
directory is adopted on the next Host cold start. To force one same-name tool
ahead of others, order it explicitly in the service PATH.

## Adopt an installed update (Linux / macOS)

Package updates belong to the official plugin command. The daemon never
self-updates, and a normal plugin install does not stop the running Host:

~~~sh
dsh plugin --profile pi-tui -- add @xmoon76/dsh-pi-tui@<version>
~~~

This section covers a PiTui package update within the SAME DSH runtime and
Profile. The running Host keeps its actual build; a normal install does not
replace it. A compatible newer Client can attach to the still-running older
Host under the same required Host/Client wire protocol (`dsh-pi-tui/local/2`)
and exact DSH runtime. To adopt the currently installed build as the Profile
Host, restart it explicitly:

~~~sh
dsh --profile pi-tui daemon restart
~~~

This stops the verified Profile Host, waits for its kernel process to exit, and
starts a fresh managed Host from the current install. On Linux a systemd unit
generated by an older install is updated in place only for its recognized
generated launch entry and install-build metadata; its other bytes, mode and
user drop-ins are preserved. On macOS the same bounded migration applies only
to a LaunchAgent whose decoded `ProgramArguments` is provably the product's
generated entry; every other byte, comment, key and user-customized argument is
preserved. A user-custom `ExecStart` or launch command is executed as written,
so the running Host may still report `compatibility=other-build` until the user
points it at the current install. An old install-build record never requires
`daemon uninstall` before an explicit restart. `restart` is an explicit user
interruption: it can interrupt a running Session, Job or Interaction and does
not promise that in-flight work survives the Host change.

Changing the DSH runtime itself is not a hot upgrade. For a published old
pairing, finish in-flight work, back up the Profile and data, stop the old
Host, and install a supported DSH/TUI pair before a cold start; see the
[DSH compatibility guide](dsh-compatibility.md) and the release notes. Do not
read this same-DSH update path as a cross-DSH migration guarantee.

A service definition belongs to the current Profile. On both platforms the user
may manage it through the native system service tools; the product preserves
user-written bytes and only updates a recognized product-generated legacy
launch field during an explicit start or restart.

## Optional local ACP listener

The split Host can expose an optional Host-owned ACP v1 listener, which is
default-off. It is not a Direct-backend listener or a second Host authority. Its Profile auto-start preference and the **current**
running listener state are separate controls. `daemon status` shows a
socket address only for a listener that has been positively verified as
enabled; never guess a socket from the home/profile path. The ACP listener,
`acp` CLI and stdio bridge remain Linux/macOS only for now; Windows honestly
reports `acp=unavailable` and creates no socket, pipe or adapter until the
Windows ACP transport is separately designed and qualified.

From an attached Split Client, `/acp` can inspect or change the current
listener state without creating a Session or updating the next-launch
preference. The headless `acp status|enable|disable` commands do the same from
an ordinary terminal without opening a TUI or starting a Host; the
[daemon management contract](../architecture/host-daemon.md#headless-acp-cli)
owns their exact stdout/exit behavior. The Direct backend refuses that runtime
control.

### External ACP client over stdio

An ACP client can use the official stdio bridge instead of opening the local
Unix socket itself. The bridge still targets the SAME running Host and existing
Session View; it does not start a Host or enable the listener:

~~~sh
# The Host must already be ready and its ACP listener enabled.
dsh --profile pi-tui daemon start
dsh --profile pi-tui daemon status        # look for acp=enabled

# Run your ACP client as a child process and speak ACP v1 over its stdio.
dsh --profile pi-tui acp stdio
~~~

Start the bridge from an ACP client that owns its stdin/stdout; do not run it
interactively expecting TUI output. It requires the default trusted Profile to
keep stdout protocol-clean: a user-added profile plugin that writes to stdout
during Profile Boot can contaminate the stream. If the Host is absent, the
listener is disabled or the target is unavailable, the command exits without
starting anything and writes a fixed `ACP_STDIO_*` diagnostic to stderr. The
bridge never auto-starts the Host; run `dsh --profile pi-tui daemon start` and
enable ACP from a connected TUI (`/acp`) or with
`dsh --profile pi-tui acp enable` first.

For contributor-level process, authentication, ACP admission and Client
detach guarantees, see [Host/Client](../architecture/host-client.md),
[daemon process ownership](../architecture/host-daemon.md) and
[ACP listener contract](../architecture/host-acp.md).

## Local ACP v1 SDK client example

This example uses the official `@agentclientprotocol/sdk@1.4.0` client and the authenticated local Host's ACP socket. ACP must first be enabled for the target Profile; the listener remains **default OFF** and is enabled only through the explicit runtime control or the profile's next-launch `autoStart` preference. Install the SDK in an **independent Node.js ≥24.9.0 project** and save the example as `acp-client.mjs`. Obtain the endpoint from `dsh --profile pi-tui daemon status`: the `acp-socket=` line is emitted only after the Host positively verifies the listener. Pass that exact value as `ACP_SOCKET`; do not derive a socket path from the profile directory. Run the example from a directory that the Host Workspace Controller will admit; an available model and credentials are also required.

~~~sh
npm install @agentclientprotocol/sdk@1.4.0
dsh --profile pi-tui daemon status
ACP_SOCKET=/path/to/verified/acp.sock \
ACP_MCP_COMMAND=/absolute/path/to/a/trusted-stdio-mcp-server \
node acp-client.mjs
~~~

This is a **local** Unix socket, not a network listener.

An ACP `session/new|resume|load.mcpServers` stdio declaration starts that
absolute executable as the Host's own user for the Session. Treat it as running
a local command: use only your own same-UID, explicitly enabled ACP socket and a
server you trust. A standard Streamable HTTP declaration uses the explicit
`type: "http"` form instead, for example:

~~~js
const httpServers = [{
  name: 'http-tools',
  type: 'http',
  url: 'https://mcp.example.test/mcp',
  headers: [{ name: 'Authorization', value: 'Bearer <your-token>' }],
}]
~~~

This is an MCP HTTP endpoint, not the local ACP transport (which remains a
same-UID Unix socket). Use the endpoint you actually trust and its final URL;
header values are real credentials and must not be shared in screenshots,
logs or diagnostics. Legacy SSE remains unsupported because no official DSH
transport exists.

The Host accepts at most four stdio/HTTP servers per Session in aggregate,
rejects relative commands, malformed arguments/environment, malformed HTTP
URLs/headers and duplicate normalized names, and rejects unadvertised
transports before any Host effect. A stdio child uses the exact Session cwd;
an HTTP-only declaration does not need a stdio child cwd (the ACP request's own
cwd still has its normal Session/Workspace meaning). The declaration is
never saved in the Profile or Host-wide MCP settings. Omit `ACP_MCP_COMMAND`
(and any HTTP declaration) to create a Session with no MCP server. HTTP follows
the official provider's normal redirect and error behavior; arbitrary
non-`Authorization` headers are not guaranteed to be stripped on a cross-origin
redirect and upstream error text is not guaranteed to be fully redacted once a
server returns it. This is the same accepted upstream limitation described in
[the ACP contract](../architecture/host-acp.md#host-owned-local-acp-v1-front-door-unix-socket).

```js
// acp-client.mjs — run from an independent Node.js client project
import { connect } from 'node:net'
import { Readable, Writable } from 'node:stream'
import * as acp from '@agentclientprotocol/sdk'

const path = process.env.ACP_SOCKET
if (path === undefined || path === '') {
  throw new Error('ACP_SOCKET must name the verified acp-socket endpoint from `dsh --profile pi-tui daemon status`')
}

const socket = connect(path)
await new Promise((resolve, reject) => {
  socket.once('connect', resolve)
  socket.once('error', reject)
})
const app = acp.client({ name: 'local-acp-example' })
  .onNotification(acp.methods.client.session.update, ({ params }) => {
    console.log(JSON.stringify(params.update))
  })
const connection = app.connect(acp.ndJsonStream(Writable.toWeb(socket), Readable.toWeb(socket)))
try {
  await connection.agent.request(acp.methods.agent.initialize, {
    protocolVersion: acp.PROTOCOL_VERSION, clientCapabilities: {},
  })
  const mcpServers = process.env.ACP_MCP_COMMAND === undefined
    ? []
    : [{ name: 'local-tools', command: process.env.ACP_MCP_COMMAND, args: [], env: [] }]
  const first = await connection.agent.request(acp.methods.agent.session.new, {
    cwd: process.cwd(), mcpServers,
  })
  try {
    const second = await connection.agent.request(acp.methods.agent.session.new, {
      cwd: process.cwd(), mcpServers,
    })
    try {
      for (const [name, sessionId] of [['first', first.sessionId], ['second', second.sessionId]]) {
        const result = await connection.agent.request(acp.methods.agent.session.prompt, {
          sessionId, prompt: [{ type: 'text', text: `Hello from ${name}` }],
        })
        console.log(`${name} stopReason:`, result.stopReason)
      }
    } finally {
      await connection.agent.request(acp.methods.agent.session.close, { sessionId: second.sessionId })
    }
  } finally {
    await connection.agent.request(acp.methods.agent.session.close, { sessionId: first.sessionId })
  }
} finally {
  connection.close()
  socket.destroy()
}
```

To borrow an existing Session, use `session.resume({ sessionId, cwd, mcpServers })` instead of `session.new`; a resume always uses the Session's original Host cwd for any stdio MCP child (an HTTP-only declaration does not use the cwd), and a different request cwd only produces a redacted diagnostic. One ACP connection may borrow up to eight Session Views, while an individual Session permits only one ACP View at a time; concurrent TUI views are unaffected. `session.close` detaches its exact view without deleting the shared Host Session, and closing an unknown or inactive Session is an idempotent success with no Host side effect. When a TUI turn is still using an MCP tool, the close returns `{}` after detaching only the ACP View: the Agent, Session and MCP lease/transport remain alive until their real Host terminal facts settle, then the Host retires the exact MCP lease. A second ACP View cannot attach that Session while an unconfirmed cleanup keeps the lease fenced. The Host's live ACP status and the next-launch auto-start preference are separate controls.
