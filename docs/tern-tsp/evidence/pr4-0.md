## Methodology

1. **Command provenance** was enumerated by expanding `registerTuiCommands`
   (`src/commands.ts:814`, ordered calls `1507-2084`) through the single
   `registerOne` seam — never by grepping file names, the completion union, or
   `LOCAL_COMMANDS`.
2. **Origin/eligibility** was traced through the one classifier
   `classifyCommandLine` (`src/domain/command/policy.ts:158-169`) and the one
   renderer-capability predicate `tspBuiltinAvailability`
   (`src/app/command/tsp-capability.ts:62-75`), with the authoritative facts
   supplied live (`hostOriginClaimOf`, the Client registry, the extension
   bridge, the skill-wrapper state).
3. **Surfaces** were enumerated from the real consumers in
   `src/app/surface/**` (which modules name `TuiApp`/`mounted()` vs a neutral
   seam) and from the real keymap `APP_KEYBINDINGS`
   (`src/tui/keybindings/definitions.ts:26`).
4. **SDK truth** was read from the *installed* package (`dist/*.d.ts`,
   `src/*.ts`) and then exercised: a disposable synthetic TSP program using the
   shipped SDK was rendered in a **real headless Tern 0.7.0** pane and driven by
   real pointer clicks through Tern's own control endpoint.
5. Every claim below is a **source→sink** chain with an observable sink, or it
   is explicitly `NOT_RUN`/`GUI_BLOCKED`.

## Executive findings (source → sink)

1. **FACT — the command gate is single and correct.** Every TUI-owned builtin
   except `/exit`+`/quit` is refused at the *post-classification* admission with
   an actionable notice and the draft restored, and no Session is created
   (`controller.ts:1683-1695`; `tsp-capability.ts:33,72`). A **genuine Host**
   command with the same spelling keeps its Host sink (proved end-to-end in
   `test/tern-tsp-direct-admission.test.ts:49`). `LOCAL_COMMANDS` is not an
   ownership authority anywhere in the production path.
2. **FACT — non-key native events are reachable but sink nowhere.** A real Tern
   pane emits `action`/`select`/`activate`/`change`/`focus`/`toggle` for real
   pointer gestures; the SDK yields them when no node handler exists; the
   renderer's `routeInput` forwards them only to the modal seat, which declines
   when no modal is open (`tsp/session.ts:713-721`,
   `tsp/interaction.ts:1264-1271`). The renderer declares **no** node
   action/handler at all, so a pointer click is not even a hit target today.
3. **FACT — the pinned SDK provides no focus read.** `surface.focus(id)` is
   write-only; the program must track inbound `focus` events itself
   ([sdk-events §4](./pr4-0-sdk-events.md)). `SessionInput` has exactly two
   variants (`key`/`event`); the 17 `TspEvent` variants are what a real pane
   produces.
4. **FACT — the TSP modal seat is the only interactive surface and it is
   keyboard-driven.** Overlays are `ui.text` rows; there are no clickable modal
   nodes. A real `overlay{modal:true}` *does* block background pointer actions,
   but not the keyboard — the app-side modal-first key route stays the authority.
5. **FACT — most application surfaces have a real owner but no TSP entry.**
   `supportsTaskCenter=false`, `supportsViewer=false`; the Plugin Manager,
   Settings, Session browser, Viewer, Task Center and all media/editor chords
   are `NOT_REACHABLE` with named owners
   ([surface matrix §3-6](./pr4-0-surface-matrix.md)). No row is marked
   `SUPPORTED` merely because a registry/port exists.
6. **FACT — the `TuiApp`-coupling surface is small and enumerable.** Only 8
   modules name `TuiApp`/`mounted()` directly; the rest consume neutral seams
   ([surface matrix §2](./pr4-0-surface-matrix.md)). This bounds the PR4B
   presentation-seam work.
7. **UNKNOWN — the early-catalog `/settings` window.** The B4 record observed
   the first `/settings` (≈53 ms after the handshake) refused, then the steady
   state routing it to the Host. This audit did **not** reproduce or root-cause
   it. It is a recorded decision item, **not** a diagnosed global readiness bug.
8. **FACT — `docs/tern-tsp.md` carried a stale B4 sentence** ("not closed
   yet") that contradicted its own state table; corrected in this PR (live doc
   only; the historical evidence file is untouched).

## PR4 proposal (not frozen)

Order-of-magnitude sizing, entry proof, required negative, and dependency for
each proposed slice. The owner freezes the split; PR4-0 does not.

### 4A — Commands & basic navigation

- **Smallest valuable slice**: implement **one** command end-to-end through a
  real TSP surface, chosen from high-value, reconnectable owners. Candidate
  ordering (evidence-based, not a preference): `/model` (`PANEL-011`) and
  `/preset` (`PANEL-012`) first — they own real settings/Agent state and reread
  it; then `/title` (`CMD-016`); then `/settings`/`/help` style panels once a
  picker/list seam exists.
- **Prerequisite**: a **non-key event → scoped intent admission** (the `4A0`
  question) *or* a keyboard-only picker built on the existing seat pattern; plus
  the existing `SubmissionController`/`commands.execute` route (already the only
  write authority).
- **Entry proof required**: real Host/Client origin → selected item → the
  original authoritative write/`reread` (e.g. `/model` must change and re-read
  the actual model owner, not merely paint a label).
- **Required negatives**: Host same-name precedence; argued-line behaviour;
  a refused TUI builtin keeps the draft; a cancel/teardown leaves no half state;
  catalog-before-ready behaviour is **defined**, not silent.
- **Do not** mechanically enable a batch of commands: each TUI command keeps its
  own availability gate.
- Without a GUI path, mouse parity must not be claimed.

### 4B — Session / Task / overlays

- **Scope**: Session list/switch/fork/resume, subagent Viewer (continuable vs
  one-shot), Task/Jobs, parked Question entry, Plugin Manager, History/Rewind —
  each through a **narrow presentation seam** over the existing application
  intent.
- **Prerequisite**: 4A's input-owner/selection/currentness/focus rules fixed
  first; **no `TuiApp` façade** and no `mounted(): TuiApp` reuse for TSP.
- **Entry proof**: real list read from the existing registry; A→B→late-A leaves
  no cross-subject state; continuable-child address is real (not treated as an
  ordinary subagent).
- **Required negatives**: stale child/viewer, forbidden concurrent modal, late
  async reply, fake Job status, `supportsViewer/TaskCenter=false` today must not
  be bypassed by disabling the guard.

### 4C — Editor & media

- **Scope**: input history, completion, clipboard text/image, `/attach`,
  external editor, copy/OSC52 — each through the existing Client/Host owner.
- **Prerequisite**: prove the pinned SDK + real pane actually support the
  intended semantics; a native `edit`/`send` capability is **not proven**
  ([sdk-events §6](./pr4-0-sdk-events.md)) — do not design on it.
- **Entry proof**: a real attachment reaches the *original Host attachment*
  route; IME/selection/native paste require physical evidence.
- **Required negatives**: no attachment laundering (an image must never become a
  placeholder string); unsupported is refused visibly; masked input never leaks.
- **Deferred with owner**: the B4 **masked physical Question** qualification —
  proposed owner: **4C** (it is an input-hardware qualification on the same
  physical test rig as IME/paste).

### 4A0 decision

**`UNDECIDABLE_WITH_REASON` — do not build it yet.**

- FACT: real Tern *does* produce the non-key events a 4A picker would need
  ([sdk-events §5](./pr4-0-sdk-events.md)), so the plan's hard `BLOCKED` trigger
  ("no native event") does **not** fire.
- FACT: a keyboard-only path is achievable with the *existing* seat pattern
  (the Question seat already routes keys and owns focus) — so the plan's "a few
  commands can enter by keyboard without a shared router ⇒ do not split 4A0"
  condition is not yet excluded.
- UNKNOWN: whether a *mouse* click on a shared picker/list node needs a single
  `event → scoped intent` admission (id → focus generation → subject/currentness
  → action) that 4A and 4B would both duplicate if built separately. The
  decisive probe is a **4A design spike** on the frozen id/generation semantics
  ([sdk-events §6.4](./pr4-0-sdk-events.md)): node ids are not generation-fenced
  by the SDK, so a shared admission must supply that fence from the app's
  subject identity.
- **Recommendation**: freeze 4A's first command with a **keyboard-first**
  picker; re-evaluate 4A0 only if that spike shows ≥2 real consumers needing the
  same id/currentness admission. If 4A0 is later proposed it must be ONE
  input-owner/identity/fail-closed primitive with no UI, with modal-first,
  unknown/stale-id, generation-rollover, dispose, reentrant-callback and
  unhandled-no-op negatives — and owner approval.
